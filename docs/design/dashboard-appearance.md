# Dashboard Appearance

The dashboard should feel like a quiet research workspace, not a pile of status cards.

## Principles

- Default to text, spacing, and hierarchy. Use borders, tinted backgrounds, and cards only when they solve a real reading problem.
- Keep the first viewport useful. A user should understand where they are, what matters now, and the next likely action without scanning decorative containers.
- Prefer fewer, stronger sections over many equal-weight panels.
- Make labels small and calm. Make primary facts readable at normal distance.
- Avoid nested boxes. A section can contain rows, lists, tables, or prose, but should not look like cards inside cards.
- Use color sparingly for state: success, warning, destructive, active. Do not tint whole regions when a small label or sentence is enough.
- Keep lines readable. Long explanations should cap around 70 characters when possible and use generous line height.
- Make controls obvious but quiet. Buttons should not dominate content unless they are the primary next step.

## Screen Review Checklist

For every screenshot pass, check:

- What is visible without scrolling?
- Does the most important user question appear in the first viewport?
- Can the eye move from title to summary to next action without crossing visual boxes?
- Are there borders or backgrounds that only decorate?
- Are there nested panels competing for attention?
- Is any text too small, too dense, or too faint to read quickly?
- Are status labels understandable without reading debug detail?
- On mobile, are primary status and actions visible without overlap or hidden controls?

## Default Visual Treatment

- Page background: plain.
- Sidebar: plain, separated by whitespace and active text treatment, not heavy lines.
- Sections: whitespace and headings.
- Rows: subtle spacing or a single hairline only when needed for tabular scanning.
- Badges: text-first, minimal fill.
- Technical/debug detail: collapsed or visually subordinate.
