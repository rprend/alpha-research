Phase 4 daily packets — Inference and evals (Days 81–95)

Delivers a KV-cached, fully-knobbed nanoGPT sampler, decode-ceiling arithmetic you can do on a napkin, and a slice of your Gutenberg benchmark running in a standard eval harness across 4 models. Prerequisite: Phase 3 checkpoint passed.

Day 81 — KV cache: implement

⏱ ~90 min · Link: karpathy/nanoGPT

Do: Add a KV cache to your nanoGPT's generate(): per layer, persist K and V tensors of shape (batch, kv_heads, seq_len, head_dim) and compute q/k/v only for the newest token each step, attending against the cache (background: section 4.2 of the phase guide). ~40 lines; diff against the reference repo only when stuck.

Explains: Why generation does O(1) work per token instead of recomputing the whole prefix — the K/V vectors of past tokens never change, so they live in VRAM as growing arrays.

Done when: Cached and uncached generate() emit identical token sequences from the same seed at temperature 0.

Day 82 — KV cache: benchmark

⏱ ~60 min · Link: Phase 4 guide

Do: Benchmark tokens/sec for cached vs. uncached generate() at generation lengths 64, 256, and 1024 on the same prompt, then plot both curves against sequence length. Also compute your cache's byte size at each length using the formula in section 4.2 of the phase guide and confirm it matches what your process actually allocates.

Explains: The quadratic-vs-flat cost difference you just bought — uncached decode re-pays the whole prefix every token, cached decode pays only for one.

Done when: A saved plot file shows the uncached curve degrading with length while the cached curve stays near-flat.

Day 83 — Sampling knobs

⏱ ~60 min · Link: The Curious Case of Neural Text Degeneration

Do: Implement temperature (logits / T), top-k, and top-p in your sampler — ~10 lines total, applied to the final logits before multinomial (background: section 4.3 of the phase guide). Then read sections 1–3 of the paper to see why naive sampling degenerates and nucleus sampling exists.

Explains: Every API's temperature=0.7, top_p=0.9 is two lines of logit surgery you have now written yourself.

Done when: Your sampler exposes all three flags, and a saved file contains generations from one prompt at T=0, T=0.7, and T=1.5 plus one top-p=0.9 sample.

Day 84 — Bandwidth arithmetic: decode ceilings

⏱ ~75 min · Link: Transformer Inference Arithmetic

Do: Read the kv-cache and latency-calculation sections of the post, then build a table of batch-1 decode ceilings using tokens/sec ≤ bandwidth / model-bytes for 8B and 70B models, each in fp16 and int4, on a 4090 (1.0 TB/s) and an H100 (3.35 TB/s) — 8 cells minimum (background: section 4.1 of the phase guide).

Explains: Decode is memory-bound: every weight must cross the VRAM bus once per token, so bandwidth — not FLOPs — sets the speed limit, which is why batching, quantization, GQA, and MoE all exist.

Done when: The 8-cell table exists in your vocabulary notebook and you can write the ceiling formula plus the H100 70B-fp16 number (~24 tok/s) from memory.

Day 85 — FlashAttention, re-read as a systems paper

⏱ ~75 min · Link: FlashAttention

Do: Re-read sections 1–3 wearing systems goggles: SRAM vs. HBM sizes and bandwidths, the tiling scheme, and the recompute-instead-of-store backward pass. Annotate every place the paper trades FLOPs for bytes-moved — the same trade governing your Day-84 table.

Explains: The memory-hierarchy argument behind your decode ceilings, applied one level down (SRAM vs. HBM instead of HBM vs. model size).

Done when: You can write the paper's two-row memory-hierarchy comparison (HBM vs. SRAM: approximate size and bandwidth) from memory and name the matrix FlashAttention never materializes.

Day 86 — vLLM and PagedAttention

⏱ ~75 min · Link: Efficient Memory Management for LLM Serving with PagedAttention

Do: Read sections 1–4, skipping kernel details, mapping each idea to its OS ancestor: fixed-size pages, the block (page) table, prefix sharing as copy-on-write. Note where continuous batching enters (background: section 4.4 of the phase guide). Your SWE instincts are the advantage here — read it as a virtual-memory paper.

Explains: Long-context serving is KV-cache memory management — vLLM is literally an OS page table for KV blocks, fixing the fragmentation your Day-82 cache would cause at scale.

Done when: You can draw from memory the block-table diagram for two sequences sharing a common prefix: logical blocks, physical blocks, and the shared block's reference count.

Day 87 — Speculative decoding

⏱ ~75 min · Link: Fast Inference from Transformers via Speculative Decoding

Do: Read sections 1–3, focusing on the rejection-sampling rule. Then work a 3-token toy example by hand: pick explicit draft probabilities q and target probabilities p, compute each token's acceptance probability min(1, p/q), and write down the resampling distribution on rejection (background: section 4.4 of the phase guide).

Explains: A cheap draft model proposes k tokens and the big model verifies them in one prefill-style pass — and the rejection rule makes the output distribution exactly the big model's, not approximately.

Done when: The hand-worked 3-token example exists on paper or in a notebook, with acceptance probabilities and the rejection-case resampling distribution computed.

Day 88 — llama.cpp hands-on: reconcile theory with a real machine

⏱ ~90 min · Link: ggml-org/llama.cpp

Do: Build llama.cpp, download a 4-bit GGUF of a 7–8B model (~4–5 GB), and run llama-cli on a fixed prompt, recording the decode tokens/sec it prints. Then predict your ceiling: look up your machine's memory bandwidth, divide by the GGUF file size, and reconcile prediction vs. observation (background: sections 4.1 and 4.4 of the phase guide). Runs free on your laptop — no GPU rental.

Explains: The bandwidth formula is not theory — your laptop's observed tokens/sec lands within ~2x of bandwidth ÷ model-bytes, and the gap itself is informative (dequant overhead, attention cost).

Done when: A note exists with three numbers: observed tok/s, predicted ceiling, and their ratio, plus one sentence explaining the gap.

Day 89 — lm-evaluation-harness: run it, then read it

⏱ ~90 min · Link: EleutherAI/lm-evaluation-harness

Do: Install the harness and run one small loglikelihood task (e.g. hellaswag, limited to a few hundred examples) on your Phase-3 SFT model — local, free, your model is tiny. Then read that task's YAML and scoring code until "the score" decomposes into the four mechanical steps: format prompt, get output, score answer, aggregate (background: section 4.5 of the phase guide).

Explains: A benchmark is physically a JSONL file plus a Python script — loglikelihood scoring never generates text, it just compares the model's log-probs over fixed candidate answers.

Done when: A harness results JSON for your SFT model exists, and you can name the YAML file and the function where the task's answers are scored.

Day 90 — LLM-as-judge and its biases

⏱ ~60 min · Link: Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena

Do: Skim the paper for the judge-bias catalog: position bias, verbosity bias, self-enhancement bias, and the human-agreement numbers that justify using judges at all. For each bias, note the paper's mitigation (background: section 4.5 of the phase guide, generative scoring).

Explains: Generative scoring leaks error at every step, and when the scorer is itself an LLM, the leaks have names — the same anchored-verifier failure you hit in your Gutenberg project, now with citations.

Done when: You can write the three named judge biases plus one mitigation each, from memory, in under 5 minutes.

Day 91 — GPQA: building a Google-proof benchmark

⏱ ~60 min · Link: GPQA: A Graduate-Level Google-Proof Q&A Benchmark

Do: Read sections 1–3, focusing on the question-writing and validation pipeline: expert writers, expert validators, skilled non-expert validators with web access, and the accuracy gap that defines "Google-proof." Then write a half-page comparing GPQA's annotator-validation protocol to your own Gutenberg label-verification step (background: section 4.6 of the phase guide).

Explains: When a famous benchmark saturates (MMLU is dead at the frontier), the replacement's whole value is its annotation pipeline — eval quality is human-protocol engineering, your existing edge.

Done when: The half-page comparison exists and names at least one GPQA practice you will adopt in your own benchmark.

Day 92 — SWE-bench: tests as the scorer

⏱ ~60 min · Link: SWE-bench: Can Language Models Resolve Real-World GitHub Issues?

Do: Read sections 1–3 plus the evaluation section: how task instances are mined from real GitHub issues, and how the repo's own test suite — not a regex, not a judge — decides resolved/unresolved. Note exactly what artifact the model must emit and what command grades it.

Explains: The most trustworthy generative scoring replaces parsing and judges with an executable oracle — real unit tests close the error leaks you cataloged on Day 90.

Done when: A note exists stating, for one SWE-bench instance, the exact model output artifact (a patch) and the exact pass condition (fail-to-pass tests pass, pass-to-pass tests still pass).

Day 93 — Custom eval, part 1: port a Gutenberg slice

⏱ ~90 min · Link: UKGovernmentBEIS/inspect_ai

Do: Skim Inspect's README, pick your harness (Inspect or lm-evaluation-harness — Inspect is the cleaner codebase, the harness has more model plumbing), and port a 30–50 example slice of your Gutenberg benchmark into a task: JSONL of examples, task definition, scorer (background: section 4.6 of the phase guide). Wire it in mock/dry-run mode first — zero API spend today, per your standing rule.

Explains: Porting your own benchmark into a standard harness forces every hidden decision — prompt format, answer extraction, aggregation — into explicit, versioned code.

Done when: The task runs end-to-end against your Phase-3 SFT model (or a mock model) and prints a score without errors.

Day 94 — Custom eval, part 2: run across models and read the failures

⏱ ~90 min · Link: Phase 4 guide

Do: Run your Gutenberg task across 3 open models (a rented 4090 covers all three: expect ~$3–5) and one API model (expect ~$1 of API spend — this is a paid run, give yourself the explicit go-ahead before launching). Build the 4-model score table, then read 10 failures per model and sort them into categories: model wrong, prompt ambiguous, scorer wrong (background: section 4.6 of the phase guide).

Explains: Error analysis is where eval numbers become meaningful — half of what looks like model failure is usually scorer or prompt failure, the construct-validity problem in miniature.

Done when: A table (4 models × score) plus an error-analysis note with at least 3 failure categories and one paragraph on what the number does and does not measure all exist in the repo.
