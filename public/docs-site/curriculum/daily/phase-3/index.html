Phase 3 daily packets — Post-training (Days 57–80)

Delivers: you personally SFT, DPO, and GRPO small open models — plus your own Phase-2 model — and the 2022–26 alignment and reasoning canon becomes readable. Prerequisite: Phase 2 checkpoint passed.

Day 57 — Feel base vs. instruct

⏱ ~60 min · Link: SmolLM2-135M-Instruct

Do: Load SmolLM2-135M base and SmolLM2-135M-Instruct locally; sample both on the same 10 prompts — 5 questions, 3 instructions, 2 raw-text continuations — and save every prompt/completion pair to one transcript file (background: the Framing section of the phase guide).

Explains: A base model is a simulator of internet text — prompt it with a question and it may continue with more questions, because that is what forums look like.

Done when: A transcript file with all 20 prompt/completion pairs exists, including at least one base-model output that continues the question instead of answering it.

Day 58 — Chat templates: there is no chat, only tokens

⏱ ~60 min · Link: HF chat templating docs

Do: Read the doc, then write a script that takes a 3-turn messages array and prints the raw string from apply_chat_template, the token IDs, and the special tokens inserted; run it through two different instruct tokenizers (SmolLM2-Instruct and Qwen2.5-Instruct) and diff the rendered strings (background: section 3.1 of the phase guide).

Explains: Roles, system prompts, and multi-turn are formatting conventions taught by fine-tuning — a template function flattens the messages array into one string the model just continues.

Done when: The script runs, and you can write the ChatML rendering of a system+user+assistant conversation from memory, special tokens included.

Day 59 — LoRA: the cheap-tuning trick

⏱ ~60 min · Link: LoRA

Do: Read sections 1–4, skim section 7; with the paper open, compute trainable-parameter counts for rank 8, 16, and 64 adapters on a 2048×2048 matrix, and the optimizer-state savings at 16 bytes/param (background: section 3.2 of the phase guide).

Explains: LoRA freezes the base weights and trains a low-rank detour W + BA, so optimizer state exists only for ~1% of parameters and an 8B fine-tune fits on a 24 GB card — QLoRA quantizes the frozen base to 4-bit and gets there even faster.

Done when: On paper, from memory, you write W + BA with correct shapes (B is d×r, A is r×d) and compute the rank-16 count for a 2048×2048 matrix (65,536) in under 5 minutes.

Day 60 — SFT: setup and launch

⏱ ~90 min · Link: TRL

Do: Rent a 4090 (~$0.50/hr, expect $2–3 total) and fine-tune SmolLM2-135M base with SFTTrainer + LoRA on a few-thousand-example SmolTalk subset; before launching, verify the loss is masked to response tokens only; log the loss curve and save the adapter (background: section 3.9, build step 1 of the phase guide).

Explains: SFT is the identical Phase-0 training loop with a chat-template dataset and the loss masked so the model never learns to predict the user's words.

Done when: The run completes with a falling loss curve logged and a LoRA adapter file of a few MB exists on disk.

Day 61 — SFT: before/after comparison

⏱ ~60 min · Link: Phase 3 guide

Do: Ask the base model and your Day-60 SFT checkpoint the same 10 questions from Day 57; build a side-by-side table and annotate which behaviors changed — answering vs. continuing, stopping at end-of-turn, persona (background: section 3.9, build step 1 of the phase guide).

Explains: Post-training is a tiny fraction of pretraining compute that selects a helpful-assistant persona from everything the simulator can already do — the most visceral demo in the curriculum.

Done when: A markdown table with 10 rows and base/SFT columns exists in your repo, with one annotation per row.

Day 62 — InstructGPT: the recipe that made ChatGPT

⏱ ~90 min · Link: InstructGPT

Do: Read sections 1–3 and figure 2 closely; skim sections 4–5; while reading, sketch the three-stage pipeline and annotate what data each stage needs and roughly how many labels (background: section 3.5 of the phase guide).

Explains: The pretrain → SFT → reward model → PPO pipeline, with humans supplying demonstrations in stage one and preference comparisons in stage two.

Done when: You can draw the three-stage pipeline from memory in under 10 minutes, with each stage's dataset type and rough size.

Day 63 — RL vocabulary, grounded in LM-land

⏱ ~60 min · Link: Spinning Up RL intro

Do: Read the Spinning Up intro page at skim depth, stopping at the derivation-heavy parts; for each term — policy, action, trajectory, reward, return, advantage, on-policy — write the RLHF translation into your vocabulary notebook (background: section 3.3 table of the phase guide).

Explains: In RLHF the policy is the LM, an action is sampling one token, a rollout is one completion, and the core move is "increase log-prob of tokens in better-than-average completions" — everything else is variance reduction.

Done when: You can reproduce the 7-row RL-term-to-RLHF table from memory in under 5 minutes.

Day 64 — Build a reward model (Bradley–Terry)

⏱ ~90 min · Link: Anthropic hh-rlhf

Do: Pull ~2k preference pairs from hh-rlhf, hold out 200; put a 1-output linear head on SmolLM2-135M and train it with the Bradley–Terry loss, −log σ(r_chosen − r_rejected) — this scale runs on your laptop in well under an hour (background: section 3.4 of the phase guide).

Explains: A reward model is your same transformer with the unembedding swapped for a 1-float head, trained on comparisons because humans are bad at absolute scores and decent at A-vs-B.

Done when: Held-out pair accuracy is above 0.60 (train on more pairs if not), and you can write the Bradley–Terry loss from memory.

Day 65 — PPO: the clipped objective, nothing else

⏱ ~60 min · Link: PPO

Do: Read sections 1–3 only — the clipped surrogate objective — and ignore the Atari/MuJoCo experiments; on paper, work out what the clip does to the gradient when the advantage is positive vs. negative and the ratio drifts past 1±ε (background: section 3.5 of the phase guide).

Explains: PPO's entire contribution is a cap on how far one update moves the policy per token, keeping it inside the region where its advantage estimates are still valid.

Done when: You can write the clipped objective — min of ratio×A and clip(ratio, 1−ε, 1+ε)×A — from memory in under 5 minutes, including what the ratio is a ratio of.

Day 66 — Goodhart: reward-model overoptimization

⏱ ~60 min · Link: Gao et al. overoptimization

Do: Read sections 1–3 and study the proxy-vs-gold reward figures; skim the scaling-law fits; note exactly where the gold score peaks and turns down as KL from the initial policy grows (background: section 3.4 of the phase guide).

Explains: The RM is a lossy proxy — optimize against it hard enough and the policy finds its errors (sycophancy, padding, confident hallucination), which is why every RLHF objective carries a KL leash to a frozen reference.

Done when: You can sketch the overoptimization curve from memory: proxy reward rising throughout, gold reward rising then falling as KL grows.

Day 67 — DPO: read it, then write the loss by hand

⏱ ~90 min · Link: DPO

Do: Read sections 1–4; then implement the DPO loss in ~10 lines of code taking policy and reference logprobs for chosen and rejected responses, and check it against TRL's implementation on one fixed random batch (background: section 3.6 of the phase guide).

Explains: The RLHF objective has a closed form — reward and optimal policy are interconvertible — so you can skip the RM and the sampling and train directly on preference pairs with a supervised loss; IPO, KTO, and SimPO are sigmoid-of-margins cousins — recognize the family, don't memorize.

Done when: Your hand-rolled loss matches TRL's to within 1e-5 on the same batch.

Day 68 — DPOTrainer run on UltraFeedback

⏱ ~75 min · Link: ultrafeedback_binarized

Do: DPO-train your Day-60 SFT checkpoint on ~5k UltraFeedback-binarized pairs with DPOTrainer + LoRA on a rented 4090 (expect $2–4); log the rewards/margins metric; afterward sample the model on 5 prompts before and after and save the outputs (background: section 3.9, build step 2 of the phase guide).

Explains: DPO is an SFT-difficulty job with RLHF-flavored results — two models in memory, no generation loop — at the cost of being offline, learning only from the dataset's responses.

Done when: The run completes with logged rewards/margins ending positive and rising, and a before/after sample file exists.

Day 70 — Llama 2: RLHF practice, candidly

Day 71 — GRPO: the algorithm

⏱ ~60 min · Link: DeepSeekMath

Do: Read section 4 of DeepSeekMath only; on paper, compute group-relative advantages for a toy group of G=4 completions, and list which of PPO's four in-memory models GRPO deletes and what replaces it (background: section 3.8 of the phase guide).

Explains: GRPO samples a group of G completions per prompt and sets each advantage to (reward − group mean)/group std — the group average replaces PPO's value network entirely.

Done when: You can write the GRPO advantage formula from memory and hand-compute the advantages for group rewards (1, 1, 0, 0) correctly.

Day 72 — GRPO build: reward function and launch

⏱ ~90 min · Link: GSM8K

Do: Write the reward function — 1.0 if the extracted final answer equals GSM8K's, else 0, plus a small format bonus for \boxed{} — and unit-test it on 20 hand-checked samples; then launch GRPOTrainer on Qwen2.5-0.5B on a rented GPU, expect $8–15 total across Days 72–74 (background: section 3.9, build step 3 of the phase guide).

Explains: Verifiable rewards swap the hackable learned RM for a script you can trust — the move behind reasoning models.

Done when: The reward function passes all 20 test samples and the GRPO run is launched and logging reward.

Day 76 — Process vs. outcome rewards

⏱ ~60 min · Link: Let's Verify Step by Step

Do: Read sections 1–3 and the main results figure; skim the rest; write the process-vs-outcome distinction into your notebook with one concrete math example where a wrong derivation reaches a right answer (background: section 3.8 of the phase guide).

Explains: Process reward models score each reasoning step, outcome reward models only the final answer — and a right answer from wrong steps is exactly what an ORM cannot punish.
