Phase 4 — Inference and evals: serving models, and knowing if they're good

Goal: two fluencies. (1) Inference systems — why generation is slow, and the stack of tricks (KV cache → quantization → batching → speculative decoding) that every deployment uses. (2) Evaluation — what benchmarks physically are, why they're broken, and how to build good ones. The second is your existing edge: your Gutenberg benchmark work (annotation pipelines, label verification, recall audits) is real eval methodology — this phase connects it to the literature.

Time: 2–3 weeks. Cost: ~$10.

4.1 Why generation is slow: the bandwidth argument

Recall your Phase-1 hand-written sampling loop: one forward pass per token. Two regimes with totally different economics:

  • Prefill (processing the prompt): all prompt tokens computed in parallel — big matmuls, compute-bound, fast.
  • Decode (generating): one token at a time, and here is the key arithmetic — to produce *each single token*, every weight of the model must be read from VRAM into the compute units once. So decode speed is bounded by memory bandwidth, not FLOPs: tokens/sec ≤ bandwidth / model-bytes. H100: ~3.35 TB/s; a 70B model in fp16 = 140 GB → ceiling ≈ 24 tokens/sec at batch 1, with the GPU's arithmetic units ~99% idle. This one calculation explains: why batching is everything (read weights once, serve 64 users), why quantization speeds up decoding (fewer bytes to move), why GQA/MoE exist, and what "memory-bound" means in every systems paper. It's the same insight as FlashAttention (Phase 2), now governing inference.

4.2 The KV cache

The fix for the Phase-1 wastefulness: when generating token t+1, the K and V vectors of tokens 1..t are *identical to last step's* — so store them. Each step then computes q/k/v only for the newest token and attends against the cached K,V. What's physically in VRAM: per layer, two tensors of shape (batch, kv_heads, seq_len, head_dim) growing by one row per token. Size = 2 × layers × kv_heads × head_dim × seq_len × 2 bytes — for Llama-3-70B at 8k context ≈ 2.6 GB *per sequence* (without GQA it'd be 8× worse — now the Phase-1 delta table's GQA row pays off). Long-context serving is KV-cache memory management, full stop.

Build (first thing this phase): add a KV cache to your nanoGPT's generate(). Measure tokens/sec before/after vs. sequence length. ~40 lines; teaches more than any paper.

4.3 Sampling knobs (they're one-liners)

All sampling controls are tiny transformations of the final logits vector, applied before multinomial: temperature = logits / T (T→0: argmax/"greedy"; T>1: flatter, riskier); top-k = zero out all but k largest; top-p/nucleus = keep the smallest set of tokens whose probabilities sum to p. Implement all three in your sampler — ~10 lines total. When an API exposes temperature=0.7, top_p=0.9, you now know the literal two lines of code that runs.

4.4 The serving stack

  • Continuous batching: requests arrive/finish at different times; the server splices new sequences into the running batch every step instead of waiting for the batch to drain. Tripled real-world throughput; standard everywhere.
  • PagedAttention / vLLM (arXiv:2309.06180): KV caches fragment VRAM like pre-virtual-memory RAM; vLLM allocates them in fixed-size pages with an indirection table — literally an OS page table for KV blocks. Read the paper as a beautiful example of classical-systems thinking imported into ML (your SWE instincts are an *advantage* here).
  • Quantization: store weights in 4–8 bits. Mechanics: per group of ~128 weights, store int4 values + one fp16 scale (w ≈ scale × int4); dequantize on the fly inside the matmul kernel. 4× fewer bytes → ~4× decode ceiling. Names to recognize: GPTQ, AWQ (weights-only); GGUF (the llama.cpp file format). Quality cost at 4-bit: small but real, larger for small models.
  • Speculative decoding (arXiv:2211.17192): a small *draft* model proposes k tokens cheaply; the big model verifies all k in one parallel forward pass (prefill-style), accepting the prefix that matches via a rejection-sampling rule that keeps the output distribution *exactly* the big model's. Free 2–3× when draft agreement is high.
  • Try it: run llama.cpp or vLLM locally with a quantized 7–8B model; reconcile observed tokens/sec with the bandwidth formula.

4.5 Evals: what a benchmark physically is

A benchmark is a JSONL file of examples plus a Python script that (1) formats each example into a prompt, (2) gets model output, (3) extracts/scores an answer, (4) aggregates a number. That's all MMLU is: 14k multiple-choice rows + a harness. Two scoring modes with very different failure surfaces:

  • Loglikelihood scoring: don't generate — compute the model's log-prob of each candidate answer ("A"/"B"/"C"/"D") and pick the highest. Deterministic, cheap, but only works for closed-form tasks.
  • Generative scoring: sample a completion, then parse it (regex for \boxed{}, run the unit tests, or — increasingly — LLM-as-judge). Every step leaks error: parsing brittleness, prompt-format sensitivity (reorder MMLU's choices and scores move *points*), judge biases (position bias, length/sycophancy bias, self-preference).

Run lm-evaluation-harness on your Phase-3 SFT model, then read the task YAML + code for one task until "MMLU 5-shot 64.2" decomposes into exact mechanical operations. Also skim UK AISI's Inspect framework — the cleanest modern eval-engineering codebase.

4.6 Why evals are broken (and why that's your opportunity)

  • Contamination: benchmarks leak into pretraining crawls; a model may have *memorized* the test set. Detection (n-gram overlap, canary strings) is imperfect; treat every headline number with suspicion.
  • Goodhart, again: labs optimize toward famous benchmarks (sometimes unintentionally via data mixture choices), so saturated benchmarks stop measuring anything (MMLU is effectively dead at the frontier; hence GPQA — arXiv:2311.12022, "Google-proof" expert questions — and SWE-bench — arXiv:2310.06770, real GitHub issues scored by real test suites).
  • Construct validity — does the number measure what its name claims? Most "reasoning" benchmarks partially measure memorization + format compliance. The papers worth emulating obsess over: human baselines, agreement audits, error analysis, held-out secrecy.

You have personally hit lexical-pool inversion, anchored verifiers, and the no-human-gold problem in your own benchmark project — that *is* the construct-validity literature, learned the honest way. Eval-building is a genuinely undersupplied research skill at every lab, and the most credible near-term lane for you to produce work people cite (more in Phase 6).

Build: write one custom eval task in lm-eval-harness or Inspect — ideally a small slice of your Gutenberg benchmark ported into a standard harness — and run it across 3 open models + one API model. Deliverable: a table, an error analysis, and one paragraph on what the number does and doesn't mean.
